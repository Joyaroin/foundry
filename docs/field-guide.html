01The shape

Foundry takes one idea from a grilling session to a merged pull request. It is built in two halves, and the seam between them is the only place it asks you anything.

The first half is a conversation, so it is a Claude Code skill. The second half must not drift, so it is a TypeScript program on the Claude Agent SDK — the loop, the concurrency cap, the stop conditions and the merge decision are all if statements a model cannot skip.

You grill, you approve the spec. After that nothing asks you a question until it hands you a pull request. The model is consulted in exactly two places for the rest of the run — what the tickets are, and the code inside one ticket. Everything else is code.

Proven 2026-08-31

A full run against harness-fixture: three tickets, two built in parallel, one correctly held behind its blocker and built in round two, all closed, PR opened, CI green, 11 tests passing, exit 0. Never exercised yet: the self-merge path, and any spoke with heavy dependencies.

02Install the hub

Once per machine. The hub holds the skills and the orchestrator; your project repos are spokes it operates on and it keeps no per-project state.

# in Claude Code
/plugin marketplace add /Users/adhamsedik/foundry
/plugin install foundry@foundry

# then, once, for the orchestrator
cd /Users/adhamsedik/foundry/orchestrator && npm install

Restart Claude Code after installing the plugin, or the skills will not load.

Credentials

Being logged in to Claude Code is enough — the SDK picks up those OAuth credentials, so a local run draws on your subscription rather than API billing. For headless or scheduled runs prefer a long-lived token; an API key also works and bills at API rates. Preflight prints which one it found.

# optional, better for unattended runs
claude setup-token
export CLAUDE_CODE_OAUTH_TOKEN=...

03Prepare a spoke

Six things, checked at preflight. The first five are usually already true; the sixth is the only file you have to write.

  • You are inside the repo, and the working tree is clean — builders branch off the integration branch, and uncommitted work would be inherited by every one of them.
  • .claude/ is gitignored. Builder worktrees live at .claude/worktrees/, and builders commit.
  • gh is authenticated, and the repo has the ready-for-agent and ready-for-human labels. Foundry creates them if missing.
  • GitHub issue dependencies are readable on the repo. This is how a blocked ticket is told from a ready one; without it foundry refuses rather than guessing.
  • Commits will be attributed to you. A local user.email override silently beats correct global settings and lands every commit Unverified. Foundry warns at preflight.
  • foundry.config.json at the repo root, declaring the gate commands.
// foundry.config.json — the minimum
{ "verify": ["npm run typecheck", "npm test"] }
Green is declared, never inferred

Foundry will not guess what "the test suite" means for your repo. Every verify command runs from the repo root and must exit 0. This is what keeps "is it green" out of a model's judgement.

04Run it

Two commands, one for each half.

The attended half

cd ~/your-project
claude
> /foundry:foundry add per-title watch reminders

It grills you in rounds, then writes a spec and publishes it as an issue. Then it asks the one question of the whole run — roughly: "Spec is #N. Approving it starts the unattended half: I write the tickets, build them all, and merge the PR if the whole queue lands green. Approve?"

The unattended half

npx tsx ~/foundry/orchestrator/src/cli.ts run <spec#> --no-merge --budget-usd 5
FlagWhat it does
--no-mergeStop at an open pull request instead of merging it. Use this for a repo's first run.
--budget-usd NCap each individual agent call. A twelve-ticket spec is thirteen or more calls, so this is not a run total.
--skip-ticketsThe tickets already exist. Use when resuming after fixing something.

For a repo's first run, use --no-merge and set maxParallel to 1, so a setup mistake surfaces once instead of three times at once.

05How it schedules

There is no plan and no dependency graph held in memory. Every round asks one question — which tickets can be built right now? — and dispatches whatever comes back. A ticket is eligible when it is open, unclaimed, labelled ready-for-agent, and has zero open blockers.

Parallelism and sequencing both fall out of that. Tickets with no blocking edge between them simply appear together; a blocked one does not appear until its blocker closes. Below is the real fixture run.

Round 1
#4 normaliseblocked_by 0 · building
#5 truncateblocked_by 0 · building
#6 slugifyblocked_by 1 · held
↓ #4 and #5 merge, gates pass, both close
Round 2
#6 slugifyblocked_by 0 · building
↓ frontier empty, nothing open → done

Within a round, builders run concurrently in isolated worktrees, capped by maxParallel. Landing is serialised: each branch merges into the integration branch, the verify commands run after that merge, and only then does the issue close. A slice that was green alone can still break a sibling merged in the same round, which is exactly what the post-merge gate catches.

06Config reference

Everything foundry knows about your repo lives in foundry.config.json. Only verify is required.

KeyTypeWhat it is for
verifystring[]Required. Commands that must exit 0 for work to count as green. Run from the repo root after every merge.
maxParallelnumberConcurrent builders. Defaults to 4. Set to 1 for a first run, or for any repo whose tests share a resource you cannot isolate.
verifyEnvobjectEnvironment for the verify commands, which run in your main working tree. Without it, a database-backed suite runs repeatedly, unattended, against whatever your own .env points at.
builderEnvobjectEnvironment for each builder. This is where per-ticket isolation comes from.
builderSetupstring[]Run in the builder's worktree before it starts. A failure fails that ticket.
builderTeardownstring[]Run after the builder finishes, pass or fail, so a failed ticket does not leak its resources.

Placeholders

Available in builderEnv, builderSetup and builderTeardown.

PlaceholderExpands toWhy you need it
{ticket}The ticket numberWhat makes one builder's resources distinct from its siblings'. A per-ticket database name is the usual use.
{repoRoot}The main checkoutA fresh worktree has none of your gitignored files. Linking to the main checkout is far cheaper than an install per ticket.

07How it ends

Every round either closes a ticket or trips a check, so the run terminates on its own. There are exactly three ways out.

StopWhat happenedWhat you get
done No open tickets left. A pull request, merged if it qualifies.
deadlock The only tickets left are blocked by ones a builder failed. A PR for what landed, plus the tickets that are stuck and why.
stall Two consecutive rounds closed nothing. The last round's failures, verbatim.

The process exits 0 only on done with nothing handed back. Anything else exits 1, so a partial run cannot be mistaken for a finished feature by whatever called it.

A failed ticket is never retried

It loses ready-for-agent, becomes ready-for-human, and stays off the frontier. Anything depending on it deadlocks — loudly, and on purpose. A loop that retries a failing ticket burns the whole budget on the one thing that cannot work. Re-running the program rebuilds nothing.

08The merge decision

Four boolean checks, all in code. A clean run merges its own pull request with a merge commit — not a squash, so the per-ticket commits and their issue numbers survive in git log.

  • The run reached done — every ticket closed, none handed back.
  • The verify commands are green on the integration branch after the last merge.
  • gh pr checks is green. A repo with no CI passes this trivially: there is nothing to be red.
  • You did not pass --no-merge.

A deadlock or stall never merges — those states contain failed tickets by definition, and merging one would put known-incomplete work on your default branch under a green-looking PR.

Never routed around

No --admin, no force, no retry of a refused merge. If branch protection or a required review blocks it, the refusal is reported verbatim and the PR stays open. A protection rule is a decision you already made.

09When it goes wrong

An interrupted run

A claimed ticket is invisible to the frontier — that is what stops two builders taking the same one. So a run killed mid-round leaves its tickets assigned with no builder behind them, and the next run finds an empty frontier and reports a deadlock that is not real.

npx tsx ~/foundry/orchestrator/src/cli.ts release <spec#>

This un-claims every open ticket under the spec. It deliberately leaves labels alone: a ticket a builder genuinely failed is ready-for-human and should stay that way.

A genuinely failed ticket

Fix it by hand, re-label it ready-for-agent, and run again with --skip-tickets. There is no retry mechanism and that is deliberate.

Leftover worktrees

Foundry creates only ticket-<n> directories and removes only those. It will never touch worktrees you created yourself, even though they share .claude/worktrees/.

10Hard-won gotchas

Five things that were invisible in the source and only appeared when the pipeline was run against real repositories. Three are fixed in foundry; two are yours to configure.

A fresh worktree has none of your gitignored files

No node_modules, and no .env. They are gitignored, so they are not in the checkout. The failure does not look like a missing file — one project's database driver reads its proxy host from .env, so the first builder migration died with ECONNREFUSED. Link both in builderSetup.

The gates run in your main working tree

Not in a worktree. So without verifyEnv, a database-backed suite runs against your real local development data, repeatedly, unattended. Point it somewhere disposable — and remember that database has to exist and be migrated before the first run.

Same-round builders collide on any file they must all create

Every builder in a round branches from the same base. If your CI requires a CHANGELOG.md entry, all of them write one, and the second merge is an add/add conflict. Foundry now resolves this: the model merges the text, code verifies no conflict markers remain, and the gates still decide green. Before that fix, a perfectly good ticket was thrown away over a changelog.

GitHub's dependency summary is eventually consistent

A freshly written blocked_by edge reads back as 0, 0, then 1. The first frontier is computed moments after ticket creation, so a blocked ticket can look ready. One run reported three tickets ready when only two were; a concurrency cap of 2 is the only reason it did not build a slice against a dependency that did not exist. Foundry now waits for every edge it wrote to become visible, and fails loudly rather than starting on data it cannot trust.

A local git identity override lands every commit unverified

A repo-local user.email silently beats correct global settings. Every commit lands Unverified with reason no_user, which you only notice by reading the repo on github.com afterwards. Foundry warns at preflight rather than refusing — plenty of repos legitimately do not sign.

11Two real configs

A repo with no shared state

Plain JavaScript, no dependencies, tests touch nothing outside the process. Almost nothing to configure.

{
  "verify": ["npm test"],
  "maxParallel": 2
}

A Next.js app whose tests need Postgres

Every builder gets its own database and its own linked dependencies; the gates get a separate database again so they never touch your development data.

{
  "verify": ["npm run typecheck", "npm test"],
  "maxParallel": 3,
  "verifyEnv":  { "DATABASE_URL": "postgres://user:pw@localhost:5432/app_foundry" },
  "builderEnv": { "DATABASE_URL": "postgres://user:pw@localhost:5432/app_t{ticket}" },
  "builderSetup": [
    "ln -sfn {repoRoot}/node_modules node_modules",
    "ln -sfn {repoRoot}/.env .env",
    "docker exec app-postgres createdb -U user app_t{ticket}",
    "npm run db:migrate"
  ],
  "builderTeardown": [
    "docker exec app-postgres dropdb --if-exists -U user app_t{ticket}"
  ]
}

If you cannot isolate a shared resource, set maxParallel to 1. Sequential is slower, but four builders racing one database fail for reasons that have nothing to do with their code — and every one of those failures costs you a ticket that is never retried.

Foundry is a private hub-and-spoke pipeline: one repo holds the skills and the orchestrator, and every issue, branch and pull request belongs to the project it runs in. Proven end to end on 2026-08-31; the self-merge path is still unexercised.
